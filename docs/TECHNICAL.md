# 当前构建适配笔记

## 已确认的行为

作者先在保留原教程流程的情况下通过 `preloadSprite("bscout")`、`initSetPlayerSprite(Player1, "bscout")` 和调色板 0 成功操控大熊。随后将同类“创建前覆盖”移到原生战斗资源加载入口。

原版角色选择界面没有大熊预览。本工具不添加格子、不更换头像，也不把大熊文件冒充 Arizona 资源。早期直接替换角色资源文件的方案未采用。

## 二进制适配

所有地址都是相对于**实际游戏主模块基址**的 RVA，只适用于 README 中指定 SHA256 的构建。不要假设 Frida 的 `Process.mainModule` 一定指向此游戏模块；启动器通过 Windows 进程对象取得真实基址。

| 项目 | RVA / 字段偏移 |
| --- | --- |
| 原生战斗资源加载入口 | RVA `0x1772f40` |
| 已验证调用返回位置 | RVA `0x1773b84` |
| 游戏原生字符串赋值函数 | RVA `0x8fbb0` |
| 场景中对局类型 | `scene + 0x9e4`，uint32 |
| P1 待加载角色字符串 | `scene + 0x20d0` |
| P2 待加载角色字符串 | `scene + 0x2130` |
| P1 调色板索引 | `scene + 0x2368`，int32 |
| 训练状态对象指针 | `scene + 0x2028` |
| 训练状态对象中的训练标志 | `+ 0x1e8`，uint8，仅记录 |

角色字符串采用该构建中的 MSVC std::string 布局：长度 `+16`、容量 `+24`；容量小于 16 时使用对象内缓冲区。修改使用原生赋值函数，不把外部字符串指针塞进游戏对象；大熊名长 6 字节。

初版对局类型判断：本地选角完成回调会写入 0；本地人机实测观察到 `type=0, training=0, P1=cow`。网络相关分支使用类型 1 / 11。初版将全部非 0 值拒绝，后经真实分享测试发现漏掉了类型 10 的训练流程，见下方修复。

2.1.0 修正上述初版判断：分享版测试日志实际出现 `fightType=10, training=1, P1=cow`，初版误拦截此训练流程。现在白名单为 `type=0 OR (type=10 AND training=1)`。网络类型 1 / 11 即使带训练标志也拒绝；类型 10 无训练标志也拒绝。仓库曾出现 `fightType > -100` 的宽泛判断，发布分享版时已替换为此白名单。

分享版使用 PyInstaller one-folder 打包 Python 3.12.14、Frida 17.24.3；冻结环境从 exe 旁写日志，从打包资源目录读取 hook。启动器通过只读 PowerShell 子进程定位游戏并验证磁盘哈希，不自动启动游戏，不修改资源。`--self-test` 不注入游戏。

## 验证边界

- 作者实测确认：普通自由训练、本地双人、本地人机，P1 选 Arizona 后可加载大熊。
- 训练及非训练本地对局的日志均确认 `cow → bscout`，P2 名称保持不变。
- `tests/hook.test.cjs` 用模拟内存检查模式过滤、P1/调色板写入、P2 不变和字节校验失败时拒绝挂钩；不连接游戏，不测试真实网络。
- 为公开发布改造了依赖安装、路径定位、会话管理与日志。原作者机器已有运行时；全新电脑的一键安装流程仍需不同环境验证。
- 尚未完整回归：每个招式、所有场地、回合结束、胜负演出、再战、录像、保存载入、多 Mod 共存。

本项目没有宣称在线兼容，也没有进行在线实测。遇到更新，应重新确认所有 RVA、字段布局和调用约定，再更新构建白名单。
